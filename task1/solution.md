## 1. LLM: локальные Hugging Face vs облачные OpenAI / YandexGPT

### Качество ответов

- Современные облачные модели (GPT‑5/4.x, YandexGPT последних поколений) всё ещё в среднем превосходят большинство
  open‑source моделей по reasoning, качеству многошаговых ответов и устойчивости к шумным документам.
- Лучшие open‑source LLM (Llama‑3.1, Qwen, Mistral/Mixtral и др.) уже дают сопоставимое качество для задач RAG по
  внутренней документации, особенно после грамотного промптинга и настройки температуры.

Вывод: для RAG по корпоративным документам хороший open‑source LLM может быть достаточен, но для максимально
качественных, «человечных» ответов и сложных рассуждений преимущество за облачными моделями.

### Скорость работы

- Облачные API дают низкую задержку за счёт мощного кластера, но есть сетевые задержки и rate‑limit.
- Локальные модели на GPU (например, 8–24 GB VRAM) при грамотном quantization и batching могут выдавать ответы за 0.5–2
  секунды, без сетевых overhead.

При правильной конфигурации GPU локальный LLM для RAG будет достаточно быстрым и предсказуемым; облако даёт хорошую
среднюю задержку, но зависимость от сети и лимитов.

### Стоимость владения и использования

- OpenAI/YandexGPT: платёж «per tokens» — удобно на старте, нет CAPEX, но при большом потоке вопросов (вся компания,
  тысячи запросов в день) стоимость стремительно растёт.
- Локальные Hugging Face: нужен сервер с GPU (или несколько), есть upfront‑cost + DevOps‑расходы, но дальнейший рост
  запросов почти не увеличивает переменную стоимость.

Вывод: для пилота и небольшой нагрузки облако дешевле и проще; при постоянной нагрузке от всей компании и долгосрочном
использовании локальная модель становится экономически выгодной.

### Удобство развёртывания

- Облачные OpenAI / YandexGPT: фактически «одна HTTP‑ручка», быстрая интеграция, не нужно заниматься MLOps.
- Локальные Hugging Face: нужно поднимать inference‑сервер (vLLM, TGI, Ollama и т.п.), следить за обновлениями моделей,
  мониторингом, масштабированием.

Для QuantumForge, где уже есть Kubernetes (EKS) и сильная инженерная команда, развёртывание локальных моделей технически
выполнимо, но всё равно дороже по операционным усилиям, чем просто использовать API.

## 2. Эмбеддинги: Sentence‑Transformers (локально) vs OpenAI Embeddings (облачно)

### Скорость создания индекса

- OpenAI Embeddings: вызовы через API, латентность 100–500 мс на запрос, но можно батчить до тысяч текстов; при
  индексировании ~20k–30k документов это займет часы и будет зависеть от сети и лимитов.
- Sentence‑Transformers локально: на CPU даёт 10–100 мс на документ, на GPU ускорение 5–10x; для десятков тысяч
  документов индекс строится за минуты–десятки минут без сетевых ограничений.

Для регулярной переиндексации внутренней базы знаний локальные Sentence‑Transformers на GPU дают более предсказуемую и
быструю индексацию.

### Качество поиска

- OpenAI text‑embedding‑3‑large / small демонстрируют очень высокое качество семантического поиска и хорошо ведут себя
  на разных доменных задачах.
- Современные Sentence‑Transformers (например, модели на базе MPNet, E5, bge) дают качество, сопоставимое с OpenAI
  embeddings для многих задач retrieval, особенно после выбора модели под юридические/технические тексты.

Для технической документации SaaS‑продукта грамотно выбранный Sentence‑Transformers даёт достаточное качество поиска,
особенно при последующей генерации ответа LLM.

### Стоимость владения и использования

- OpenAI Embeddings: $0.00002–0.00013 за 1k токенов; при миллионах токенов в месяц это десятки–сотни долларов, но без
  инфраструктурных затрат.
- Sentence‑Transformers: нужна машина (желательно GPU), но после этого индексирование и поиск не стоят «per token»,
  только инфраструктура (например, условные $200/мес за GPU‑инстанс по оценке авторов).

При регулярной индексации растущей базы (~400 новых страниц в месяц) и активном онлайновом поиске локальные эмбеддинги
будут выгоднее в долгосрочной перспективе, особенно если тот же GPU используется и для LLM.

## 3. ChromaDB vs FAISS как векторные хранилища

### Скорость поиска и индексации

- FAISS — высокопроизводительная C++‑библиотека, особенно с GPU, даёт минимальную задержку и масштабируется до
  миллиардов векторов.
- ChromaDB — ориентирован на удобство разработки, обеспечивает хорошие, но не максимальные показатели, оптимален для
  миллионов векторов, а не миллиардов.

Для объёмов QuantumForge (десятки–сотни тысяч документов → несколько миллионов векторов с chunking) ChromaDB по
производительности достаточен, FAISS нужен, если планируется экстремальное масштабирование или жёсткие требования по
latency.

### Сложность внедрения и поддержки

- FAISS — это библиотека для поиска по векторным массивам; нужно самостоятельно решать хранение метаданных, persistence,
  sharding, REST‑обёртку и т.п.
- ChromaDB — полноценная векторная БД с встроенной персистентностью, метаданными, фильтрами и удобным Python‑API;
  подходит для построения RAG‑систем «из коробки».

Для команды приложения (а не исследователей по векторным индексам) ChromaDB даёт намного более простой и быстрый путь к
production.

### Удобство в работе

- ChromaDB сфокусирована на DX (developer experience): коллекции, фильтрация по метаданным, интеграция с
  LLM‑фреймворками (LangChain и др.).
- FAISS требует большего ML/IR‑экспертного уровня и собственного «обвеса» ради функций, которые Chroma предоставляет
  сразу (метаданные, фильтры, REST‑слой).

### Стоимость владения

- Обе технологии open‑source; стоимость — это сервера + поддержка. ChromaDB как Python‑сервис добавляет накладные
  расходы по памяти и CPU, FAISS как библиотека — более «тонкое» решение, но требует разработки вокруг.

Для QuantumForge базовый сценарий (несколько миллионов векторов, один кластер приложения) можно комфортно обслужить
ChromaDB‑инстансом на том же или соседнем сервере, где крутится RAG‑сервис.

## 4. Рекомендуемая конфигурация сервера для RAG‑бота

Исходя из объёма документов и сценариев использования (десятки–сотни активных пользователей, пик — сотни запросов в
час), можно ориентироваться на такие конфигурации:

- **Минимальный GPU‑сервер для пилота (локальный LLM + эмбеддинги + ChromaDB)**
    - CPU: 8 vCPU
    - RAM: 32 GB
    - GPU: 1× NVIDIA RTX A4000 / L4 / аналог с 24 GB VRAM
    - Диск: 500 GB SSD (инференс, индексы, логи)  
      Такая машина потянет 7–14B‑модель в 4‑битном квантовании, Sentence‑Transformers и ChromaDB.

- **Производительный сервер (выше качество модели, больше одновременных запросов)**
    - CPU: 16 vCPU
    - RAM: 64 GB
    - GPU: 1× A40 / L40S / H100‑подобный с 48 GB VRAM
    - Диск: 1 TB SSD  
      Подходит для более крупных моделей (14–34B) и высоких нагрузок.

- **Без GPU (облачный LLM + локальные эмбеддинги/Chroma)**
    - CPU: 8–16 vCPU
    - RAM: 32–64 GB
    - GPU: нет  
      В этом варианте inference LLM идёт через OpenAI/YandexGPT, а локально крутятся только ChromaDB +
      pre/post‑processing и, при желании, CPU‑эмбеддинги (но медленнее).

## 5. Варианты архитектуры и выбор лучшего

Ниже — 4 варианта с краткой сравнительной таблицей, затем выбор.

### Вариант A: Полностью облачный (OpenAI/YandexGPT + OpenAI Embeddings + внешняя векторная БД)

- LLM: OpenAI / YandexGPT API.
- Эмбеддинги: OpenAI Embeddings.
- Векторная БД: облачный сервис (например, Pinecone) или hosted Chroma.
- Плюсы: минимальный time‑to‑market, нет своей ML‑инфраструктуры, отличное качество.
- Минусы: вся документация уходит в облако, что плохо для SOC 2/конфиденциальности; рост стоимости при массовом
  использовании; зависимость от внешних провайдеров.

### Вариант B: Гибридный — облачный LLM + локальные эмбеддинги и векторная БД

- LLM: OpenAI/YandexGPT API (без передачи самых чувствительных документов или с обфускацией).
- Эмбеддинги: локальный Sentence‑Transformers (на CPU или GPU) в AWS VPC.
- Векторное хранилище: ChromaDB в Kubernetes кластере (EKS).
- Плюсы:
    - Внутренние документы не уходят в сторонние embedding‑API, индекс строится внутри VPC.
    - Качество генерации от сильной облачной модели.
    - Умеренные инфраструктурные требования (GPU не обязателен для пилота).
- Минусы:
    - Текст вопроса и retrieved‑контент всё равно отправляются в облако (если не обфусцировать).
    - Переменная стоимость токенов LLM.

### Вариант C: Полностью локальный open‑source стек (LLM + эмбеддинги + ChromaDB)

- LLM: Llama‑3.1 / Qwen / Mistral‑подобная модель, развёрнутая на GPU в EKS.
- Эмбеддинги: Sentence‑Transformers.
- Векторная БД: ChromaDB (или ChromaDB + FAISS backend).
- Плюсы:
    - Данные не покидают AWS‑аккаунт компании; хорошо для SOC 2 и внутренней безопасности.
    - Предсказуемая стоимость (серверы), удобно масштабировать, можно адаптировать модель под домен.
    - Можно позже упаковть как продукт для клиентов.
- Минусы:
    - Ниже максимум по качеству, чем у топ‑облачных моделей.
    - Требуются усилия MLOps и поддержка GPU‑инфраструктуры.

### Вариант D: Локальный векторный слой + FAISS для максимальной производительности

- LLM: либо локальный, либо облачный (как в B/C).
- Эмбеддинги: Sentence‑Transformers.
- Векторное хранилище: FAISS как основной поиск, поверх — свой слой метаданных и persistence, либо гибрид ChromaDB +
  FAISS.
- Плюсы: максимальная скорость поиска и масштабируемость до очень больших объёмов.
- Минусы: усложнение архитектуры, больше кастомного кода, избыточно для текущих объёмов QuantumForge.

## Итоговые рекомендации и выбор векторной БД

Для кейса QuantumForge разумная стратегия:

1. **Рекомендуемая векторная БД для бота — ChromaDB**.
    - Даёт из коробки persistence, работу с метаданными (пространства/сервисы/типы документов) и простую интеграцию с
      Python‑стеком, которым компания уже активно пользуется.
    - На объёмах до миллионов векторов обеспечит хорошую скорость и простоту эксплуатации без необходимости писать
      собственный «мини‑Pinecone» поверх FAISS.

2. **На ближайший год основной рекомендуемый вариант архитектуры — Вариант C (полностью локальный open‑source стек на
   AWS EKS)**:
    - Соответствует требованиям к безопасности и SOC 2: документы и запросы остаются внутри AWS‑аккаунта компании.
    - Инфраструктура (EKS, Python/Go‑микросервисы) уже знакома команде, а R&D‑подразделение может взять на себя
      поддержку LLM‑инференса и ChromaDB.
    - Стоимость владения предсказуема: одна/несколько GPU‑нод для LLM и эмбеддингов, CPU‑нод(ы) для ChromaDB и ETL.

3. **Альтернатива для быстрого пилота — Вариант B (облачный LLM + локальный поиск)**:
    - Можно начать с OpenAI / YandexGPT в качестве LLM, при этом построить локальный пайплайн индексации и ChromaDB.
    - После подтверждения ценности (снижение времени поиска, повышение продуктивности) мигрировать LLM на локальный
      open‑source сервер, не меняя векторный слой.

4. **FAISS целесообразно рассматривать как опцию позже** (Вариант D) при:
    - росте индекса до десятков миллионов векторов,
    - жёстких SLA по latency (субмиллисекундный поиск),
    - готовности инвестировать в более сложную инфраструктуру и свой metadata/persistence‑слой.
