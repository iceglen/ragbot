# Проект RAG-бота

Этот проект реализует бота с извлечением и генерацией (RAG) для запросов к внутренней документации.

## Технологический стек

Проект реализован на **Java 25** с использованием **Maven** в качестве системы сборки. Основу приложения составляет *
*Spring Boot** с интеграцией **Spring AI** для работы с LLM-моделями и векторными хранилищами.

## Выбор технологий

Хотя изначальное задание предполагало использование Python-стека для RAG-систем, в данном проекте был сделан выбор в
пользу Java/Spring AI по следующим причинам:

- **Spring AI** — молодой, но активно развивающийся проект, который уже предоставляет большинство основных сценариев
  работы с LLM
- **Инфраструктурная зрелость** — Spring Boot и экосистема Spring предоставляют проверенные решения для построения
  production-приложений
- **Накопленный опыт** — использование Java и Spring позволяет применить уже имеющийся опыт разработки
  enterprise-приложений к области AI/ML
- **Типизация и безопасность** — статическая типизация Java и развитая система модулей способствуют созданию более
  надёжного и сопровождаемого кода

Данный подход демонстрирует возможность построения полноценных RAG-систем на Java-стеке с использованием современных
инструментов.

## Задания

### Задание 1

Первое задание находится в папке `task1`. Оно содержит анализ выбора технологий для построения RAG-системы.

### Задание 2

Второе задание расположено в папке `data`. Данные проходят многоступенчатую обработку по следующему пайплайну:

- `raw` → `clean` → `filtered` → `dereferenced` → `masked` → `replaced`

Словарь замен (маппинг оригинальных терминов на заменённые) находится в файле `data/masked-mapping.json`.

**Важное замечание:** Задание 2 выполнялось автоматически как часть задания 6, а не вручную. Весь пайплайн обработки
данных реализован в классе `BotDataScheduler` (`src/main/java/ru/artem/papyan/ragbot/scheduler/BotDataScheduler.java`) и
выполняется согласно настройкам cron'а (`0 0 0 15,28 * ?`).

### Задание 3

В третьем задании использовались модели, отличные от предложенных в задании 1, из-за ограниченности ресурсов:

- **gpt-oss:20b** - чат-модель для генерации ответов
- **qwen3-embedding:8b** - модель для создания эмбеддингов

Разбивка текста на чанки настроена один раз в методе `tokenTextSplitter` (
`src/main/java/ru/artem/papyan/ragbot/config/BeanConfig.java`), который конфигурирует бин токенизатора с параметрами
`minChunkSizeChars=10` и `keepSeparator=true`.

В результате обработки созданы два SQL-скрипта для базы данных:

- `init/pgvector-init.sql` - инициализация таблицы `vector_store` с расширениями vector, hstore, uuid-ossp
- `init/vector_store_202601151739.sql` - таблица с данными документов и их эмбеддингами

**Важное замечание:** Качество полученных данных значительно отличается от ожидаемого из-за использования менее мощных
моделей по сравнению с промышленными решениями.

#### Компоненты обработки данных (из класса `BotDataScheduler`):

1. **RawDataCollector** - сбор сырых данных из внешних источников
2. **RawDataCleaner** - очистка и нормализация сырых данных
3. **CleanDataDereferencer** - разрешение ссылок и зависимостей между документами
4. **CleanDataFictionalFilterer** - фильтрация вымышленного контента
5. **FilteredDataMasker** - маскирование информации
6. **CleanDataReplacer** - замена терминов согласно словарю маппинга
7. **DocumentProcessingService** - финальная обработка документов (разбивка на чанки, создание эмбеддингов, сохранение в
   БД)

#### Результаты обработки:

- В базу данных загружено **600 документов**
- Каждый документ разбит на чанки (количество чанков указано в метаданных каждого чанка в полях `chunk_index` и
  `total_chunks`)
- Общее время обработки всех документов составило **примерно 10 минут** на процессоре Apple M1 Max

### Задание 4

Четвёртое задание реализует клиентскую часть для общения пользователей с RAG-ботом. Предоставлены два способа
взаимодействия:

1. **REST API** - метод `processRequest` в классе `TestController` (
   `src/main/java/ru/artem/papyan/ragbot/controller/TestController.java`), принимающий POST-запросы по эндпоинту
   `/process-query`
2. **Telegram-бот** - интеграция через Telegram API:
    - `TelegramApi` (`src/main/java/ru/artem/papyan/ragbot/messenger/TelegramApi.java`) - обёртка для работы с Telegram
      Bot API
    - `TelegramWorker` (`src/main/java/ru/artem/papyan/ragbot/messenger/TelegramWorker.java`) - обработчик входящих
      сообщений и отправки ответов

**Особенности SYSTEM PROMPT:**

- В SYSTEM PROMPT реализована защита от prompt injection атак
- Процесс мышления (chain-of-thought) LLM не визуализируется для конечного пользователя

**Примеры диалогов:** скриншоты взаимодействия с ботом находятся в папке `screenshots` (положительные примеры в
`screenshots/positive`, отрицательные в `screenshots/negative`)

### Задание 5

Пятое задание посвящено безопасности RAG-системы и защите от зловредного контента:

- **Зловредный файл** расположен в папке `./data/toxic/root.txt`
- **Результаты обработки** с защитой и без защиты представлены на скриншотах в папке `./screenshots/swordfish`
- **Тестирование качества ответов**: вопросы к боту по контексту и без контекста расположены в папках:
    - `./screenshots/positive` - примеры корректных ответов с использованием контекста
    - `./screenshots/negative` - примеры ответов без контекста или с некорректными ответами

**Механизм защиты:** защита от атак через текстовые документы была выстроена на уровне запроса к LLM с использованием
специальных инструкций в SYSTEM PROMPT, фильтрующих потенциально опасные команды и предотвращающих выполнение зловредных
инструкций.

### Задание 6

Шестое задание посвящено автоматизации сбора и обработки данных. В рамках проекта задания 2 и 6 являются равнозначными,
поскольку изначально был сделан упор на автоматизацию процесса сбора и обработки данных.

**Источник данных:** данные извлекаются из Fandom WIKI API, что позволяет автоматически получать актуальную информацию
из вики-ресурсов.

**Хранилище данных:** в качестве хранилища используется локальная папка, но архитектура позволяет использовать
примонтированные S3-хранилища или NFS-папки.

**Процесс обработки:**

- Детальный пайплайн обработки данных описан в **задании 2** (путь по папкам в хранилище, который проходят данные от
  HTML-страниц до обработанного текста с заменами)
- Компоненты обработки перечислены в **задании 3** в порядке, соответствующем прохождению данных от начала до конца
  пайплайна
- Процесс включает следующие этапы: сбор данных из API, очистка HTML, фильтрация контента, разрешение ссылок,
  маскирование и замена терминов, создание эмбеддингов и сохранение в векторную БД

**Автоматизация:**

- Процесс реализован в виде cron-задачи, выполняющейся каждые 2 недели
- Расписание задаётся через переменную окружения `RAG_DATA_CRON`, которая по умолчанию имеет значение
  `"0 0 0 15,28 * ?"` (настраивается в конфигурационном файле `src/main/resources/application.yaml`)

**Особенности реализации:**

- Время отработки всего пайплайна варьируется в зависимости от мощностей используемых LLM-моделей
- Предусмотрен механизм быстрого отказа (early exit) в случае, если изменений данных нет:
    - В классе `RawDataCleaner` (`src/main/java/ru/artem/papyan/ragbot/preprocessing/RawDataCleaner.java`) реализован
      механизм сравнения новых и старых данных через метод `isUpdateNeeded`
    - Если новых данных не обнаружено, пайплайн прерывается на раннем этапе, экономя вычислительные ресурсы

**Визуализация процесса:** упрощённая схема пайплайна расположена в файле `task6/pipeline.puml`. Скриншот схемы доступен
по
ссылке: [PlantUML схема](https://www.plantuml.com/plantuml/png/SoWkIImgAStDuN9Bp4l9ptKCy5JGjLC8SdGlo2n8pSdCIrMmKaXBBKdEoCnBLqX9B4daGf83AVNnyGKgAIXABIZAJqujBeQh0qg0vCDIaqloYuA166HKQcvIQaeAI4qnK2GnFPNB8JKl1MW_0000)

**Итог:** система обеспечивает полностью автоматизированный пайплайн сбора, обработки и индексации данных с минимальным
вмешательством оператора.

### Задание 7

Седьмое задание посвящено оценке качества работы RAG-системы и её ограничениям:

**Зависимость от мощностей LLM:** Качество базы знаний очень сильно зависит от вычислительных мощностей LLM, поскольку
процесс обработки данных (очистка, фильтрация, создание эмбеддингов) критически опирается на возможности модели.

**Ограничения маленьких моделей:** При использовании относительно небольших моделей (например, gpt-oss:20b, применённой
в текущем проекте) модель физически не может содержать знания со всего интернета и способна отвечать только в рамках
предоставленного контекста. При любом отклонении от тематики загруженных документов RAG-система не сможет дать
осмысленный ответ.

**Логирование:** Обработка входящих запросов и отправка ответов логируются через стандартный вывод (stdout). Объём и
детализация логов варьируются в зависимости от настроенного уровня логирования (DEBUG, INFO и т.п.).

**Автоматическое тестирование:** Для проверки корректности работы системы реализован unit-тест `RagEvaluationTest` (
`src/test/java/ru/artem/papyan/ragbot/RagEvaluationTest.java`), который использует заранее подготовленный список
вопросов из файла `data/golden-questions.txt`. Тест проверяет два сценария:

- Вопросы, на которые система должна дать ответ (известные сущности из обработанных документов)
- Вопросы, на которые система должна ответить, что информация отсутствует (неизвестные сущности)

Тест гарантирует, что RAG-система адекватно распознаёт границы своей базы знаний и не выдаёт ложных ответов за пределами
предоставленного контекста.
